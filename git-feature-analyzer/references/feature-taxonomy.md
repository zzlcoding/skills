# 功能分类与跨分支关联

本文件定义 AI 功能识别阶段使用的功能分类体系，以及跨分支功能去重阶段使用的关联关系分类。

## 1. 功能分类

每个识别出的功能必须归入以下 8 类之一：

| 分类标识 | 中文名称 | 说明 |
|---|---|---|
| `new_feature` | 新增功能 | 新增业务或技术能力 |
| `feature_enhancement` | 功能增强 | 扩展已有功能 |
| `bug_fix` | Bug 修复 | 修复已有功能缺陷 |
| `performance_optimization` | 性能优化 | 优化执行效率和资源占用 |
| `architecture_change` | 架构调整 | 模块重构和架构调整 |
| `configuration_change` | 配置调整 | 配置项和参数调整 |
| `feature_removal` | 功能删除 | 删除已有功能 |
| `non_functional_change` | 非功能性修改 | 注释、格式、变量重命名等 |

### 1.1 分类判定要点

| 代码变化现象 | 归类 |
|---|---|
| 新增类/接口/数据结构 + 业务实现 | `new_feature` |
| 在已有函数中新增分支、参数、返回值类型 | `feature_enhancement` |
| 修改 if/while/异常处理以纠正行为 | `bug_fix` |
| 引入缓存、并行、索引、批处理 | `performance_optimization` |
| 拆分/合并模块、抽象基类、引入中间层 | `architecture_change` |
| 修改配置文件、默认值、环境变量 | `configuration_change` |
| 删除类/接口/函数/文件 | `feature_removal`（若对应旧功能）或 `non_functional_change`（若仅清理无用代码） |
| 注释、命名、格式、空行、import 排序 | `non_functional_change` |

### 1.2 归类边界

- **重构 vs 架构调整**：纯函数抽取、变量重命名属于 `non_functional_change`；模块边界重新划分、引入新抽象层属于 `architecture_change`。
- **Bug 修复 vs 功能增强**：修复既有行为偏差属于 `bug_fix`；新增可配置项、新增可选参数属于 `feature_enhancement`。
- **新增 vs 删除**：同一文件既新增又删除大量代码时，分别评估两侧的业务语义，不可一概而论。

## 2. 跨分支关联关系

完成各分支独立分析后建立统一功能库。每个跨分支匹配必须落到以下 5 类之一：

| 关系标识 | 中文名称 | 含义 |
|---|---|---|
| `IDENTICAL` | 完全相同 | 功能和实现基本相同 |
| `SAME_FEATURE` | 相同功能 | 业务能力相同，但实现不同 |
| `RELATED` | 相关功能 | 功能存在依赖或扩展关系 |
| `INDEPENDENT` | 独立功能 | 功能之间没有明显关联 |
| `UNCERTAIN` | 无法确定 | 证据不足，需要人工确认 |

### 2.1 关系判定优先级

按以下顺序逐级判定，直到命中：

1. **Commit SHA 相同**：直接判 `IDENTICAL`。
2. **Patch ID 相同**：判 `IDENTICAL`（代码补丁等价）。
3. **功能实现结构相同**（类、接口、关键算法）：判 `IDENTICAL`。
4. **业务能力相同，实现不同**（不同语言/不同框架/不同算法）：判 `SAME_FEATURE`。
5. **存在依赖或扩展**（一方依赖另一方/一方扩展另一方）：判 `RELATED`。
6. **功能之间无明显关联**：判 `INDEPENDENT`。
7. **证据不足**：判 `UNCERTAIN`，不自动合并。

### 2.2 去重规则

- 不能仅根据功能名称合并。
- 不能仅根据文件路径合并。
- 需要考虑：业务目的、输入输出、接口行为、具体实现。
- 不同实现可能实现相同业务功能；相似代码也可能服务于不同业务功能。
- 每个跨分支关联必须记录判断依据（Commit SHA/Patch ID/代码片段对比/AI 语义判断）。
- 置信度低于 0.7 的功能不要自动合并，保留为 `UNCERTAIN`。

### 2.3 关联证据记录

每个跨分支关联应至少包含以下信息：

```json
{
  "关系类型": "IDENTICAL",
  "判断依据": [
    "Commit SHA 相同：abc1234",
    "Patch ID 相同：deadbeef..."
  ],
  "置信度": 0.99,
  "是否需要人工确认": false
}
```

### 2.4 常见关联模式示例

| 场景 | 关系 |
|---|---|
| 主干提交 `abc1234` 出现在 5 个分支历史中 | `IDENTICAL` |
| 两个分支独立实现 OAuth 登录，但用不同 SDK | `SAME_FEATURE` |
| 分支 A 新增缓存，分支 B 在 A 的缓存基础上加 LRU 淘汰 | `RELATED` |
| Cherry-pick 引入的相同 patch | `IDENTICAL` |
| 两个分支都「新增日志模块」但功能点、接口完全不同 | `INDEPENDENT` |
| 仅凭功能名称相似，代码、接口、用途无证据 | `UNCERTAIN` |

## 3. 统计指标定义

| 指标 | 含义 |
|---|---|
| Commit 数量 | 原始 `git log` 输出条数 |
| Patch 数量 | 去重后独立 Patch 数量（按 Patch ID） |
| 分支功能数量 | 单个分支独立识别出的功能数（含功能增强、Bug 修复等所有分类） |
| 仓库唯一功能数量 | 跨分支去重后的功能数 |
| 项目独有功能数量 | 仅出现在某分支、跨分支去重后仍唯一的功能数 |
| 多分支共享功能数量 | 跨分支 `IDENTICAL` / `SAME_FEATURE` 关联的功能数 |
| Cherry-pick 关联功能数量 | 通过 Cherry-pick 引入的功能数 |
| 待人工确认功能数量 | 标记 `UNCERTAIN` 或 `是否需要人工确认=true` 的功能数 |

**重要：以上指标不可混用。** 例如分支功能数量是「未经跨分支去重」的数量，仓库唯一功能数量是「去重后」的数量。
